本章缩写：ROS = Robot Operating System（机器人 / 操作 / 系统，名字叫操作系统，其实是一套库和工具）；DDS = Data Distribution Service（数据 / 分发 / 服务：工业标准的发布订阅中间件）；RMW = ROS MiddleWare（ROS 中间件接口）；rcl = ROS Client Library（ROS 客户端库的 C 核心）；rclpy / rclcpp = rcl + Python / C++；QoS = Quality of Service（服务 / 质量：通信可靠性等设置）；API = Application Programming Interface（应用 / 编程 / 接口）；UDP = User Datagram Protocol（用户 / 数据报 / 协议：一种网络传输协议）；IDL = Interface Definition Language（接口 / 定义 / 语言）；rosidl = ROS IDL；VLA = Vision-Language-Action（视觉 / 语言 / 动作模型）；IK = Inverse Kinematics（逆 / 运动学：由手的位置反算关节角）；LTS = Long-Term Support（长期支持版）；JSON = JavaScript Object Notation（JavaScript / 对象 / 表示法：代码对照里代替 CDR 演示序列化）；CDR = Common Data Representation（通用 / 数据 / 表示：DDS 的序列化格式）。全部缩写见 附录 · 缩写与术语表

层 是什么 你要不要碰
能力包 Nav2、MoveIt 2、ros2_control、tf2：别人写好的一组节点 拿来用、配参数
你的节点 每个只干一件事；命令行、rviz2、rosbag2 这些工具也都是节点 你写

一句话：你只写节点、调客户端库；rcl 往下全是 ROS 2 内部，中间件可以整块换掉而代码不改。

图 2：核心流程（一条消息走一趟）

可交互版：animations/01-message-flow.html。

用官方 talker / listener 例子：talker 每 0.5 秒往 /chatter 发一句话，listener 收到就打印。

建立连接（只做一次）
  ① 启动：各自创建 publisher / subscription（只在本进程登记）
  ② 发现：中间件在同一 ROS_DOMAIN_ID 里自动广播"我是谁、发收什么"，没有中心服务器
  ③ 匹配：话题名相同 + 类型相同 + QoS 兼容，三项都满足才连上
每条消息（循环）
  ④ 发布：定时器回调里 pub.publish(msg)
  ⑤ 往下：rclpy → rcl → rmw
  ⑥ 序列化：中间件把对象变成字节
  ⑦ 传输：UDP / 共享内存
  ⑧ 排队：接收端放进订阅队列（深度 10，满了挤掉最旧的）
  ⑨ 等待集：executor 在 spin() 里发现队列有数据
  ⑩ 往上 + 反序列化：字节还原成对象
  ⑪ 回调：调用你的 callback(msg)

三个看点：

  1. 连接是"自动发现 + 三项匹配"建立的（nodes/About-Discovery.rst 第 26–34 行）。QoS 不兼容就连不上，只打一条警告，新手常踩。
  2. 消息在发送端往下走（对象 → 字节），在接收端往上走（字节 → 对象）。所以 Python 发、C++ 收没问题。
  3. 回调不是消息一到就跑：要等 executor 在 spin() 里通过等待集（wait set）发现有数据才调用（client-libraries/About-Executors/About-Executors.rst 第 60–71 行）。忘了 spin()，回调永远不会执行。

你的代码只出现在 ① 和 ⑪，中间九步都是 ROS 2 替你做的。

第 1 步 · 节点与"管道"

ROS 不是操作系统。 它不像 Windows、Ubuntu 那样管硬盘和内存，而是装在 Ubuntu 上面的一套工具和库。官方原话说它是机器人各部分之间通信的 "plumbing"（管道）（materials/ros2_documentation/source/About-ROS.rst §Framework）。

白话类比：餐厅后厨。

  • 每个厨师只干一件事：一个切菜，一个炒菜，一个摆盘。
  • 切菜的切好了，就放到传菜口。他不用知道是谁来拿。
  • 炒菜的只盯着传菜口，有菜就拿。他也不用知道是谁切的。

换到 ROS 里：

后厨 ROS 2 说明
一个厨师 节点（node） 一个干一件事的程序
一个传菜口，写着名字"切好的菜" 话题（topic），有名字，如 /image 数据放在这里
往传菜口放菜 发布（publish）
盯着传菜口拿菜 订阅（subscribe）

机器人例子：一台看到红球就追的小车。

[camera_driver] --/image--> [ball_detector] --/ball_position--> [chaser] --/cmd_vel--> [motor_driver]
   读相机               在图里找红球                  算该往哪开             驱动轮子

方括号是节点，箭头上是话题名。官方的要求是"每个节点只做一件逻辑上的事"（ROS-Framework/About-Nodes.rst 第 41 行）。

这样拆有什么好处：

  1. 可替换：换一个牌子的相机，只需换掉 camera_driver。只要它照样往 /image 发图，后面的节点一行都不用改。
  2. 能分开跑：节点可以在同一个进程、不同进程，甚至不同电脑上，彼此照样通信（About-Nodes.rst 第 40 行）。比如 ball_detector 放到带 GPU 的电脑上，motor_driver 留在小车上。
  3. 可复用：别人写好的 camera_driver、导航节点，拿来就能接上。

和本仓库的连接：学的 VLA 策略部署到机器人上时，就是一个节点：订阅 /image 和 /joint_states，发布动作。

第 2 步 · 节点之间的四种说话方式

接着用后厨类比。厨师之间不只有"传菜口"一种沟通方式：

方式 后厨类比 特点 机器人例子 定义文件
话题 topic 传菜口：做好就放，谁要谁拿 单向、持续不断；多对多；发的一方决定什么时候发 相机 30 Hz 发 /image；关节状态 /joint_states .msg
服务 service 打内线电话问一句："今天还有牛排吗？"对方马上答 一问一答；问的一方等着答案；必须很快结束 问逆运动学（IK）的解；问"电量多少" .srv（请求 --- 回复）
动作 action 点外卖：下单 → 不断收到"骑手到哪了" → 送达；中途能取消 耗时长；中间有进度反馈；能取消 / 抢占 "导航到厨房"（几十秒）；"机械臂去抓杯子" .action（目标 --- 结果 --- 反馈）
参数 parameter 每个厨师灶台上的旋钮：火候、咸淡 不是消息，是节点自己的配置；不改代码就能调；运行中也能改 ball_detector 要找的颜色；最高车速；每个节点都有的 use_sim_time —

怎么选（官方的经验规则，ROS-Framework/interfaces/Topics-Services-Actions.rst）：

  • 数据源源不断 → 话题。
  • 问一句、马上要答案 → 服务。官方特别强调：服务不能用来做耗时长的事，因为对方一直在等，出了意外也没法中途叫停。
  • 要花一段时间、想看进度、可能中途取消 → 动作。官方说动作最重要的性质就是能被干净地抢占（preempt）。
  • 是节点的设置，不是要传的数据 → 参数。

几个容易忽略的细节：

  1. 话题是匿名的：订阅者一般不知道也不关心是谁发的（About-Topics.rst §Anonymous）。这正是第 1 步"可替换"的来源。
  2. 话题是强类型的：消息里每个字段的类型和单位都定死。比如 IMU 消息里的角速度单位规定是 rad/s（About-Topics.rst §Strongly-typed）。
  3. 一个服务名、一个动作名只能有一个服务端（server），但可以有很多客户端（client）。话题则随便多少个发布者和订阅者（About-Services.rst、About-Actions.rst）。
  4. 参数属于某个节点，节点关掉参数就没了（About-Parameters.rst §Parameters in ROS）。

回头看练习 1-2：想从追红球改成追蓝球，最省事的做法是给 ball_detector 一个参数 target_color，运行时用 ros2 param set 改成 blue，一行代码都不用改；motor_driver 完全不用动。

和本仓库的连接：VLA 策略节点订阅图像和关节状态用话题；上层"去叠毛巾"这种几十秒的任务适合做成动作；控制频率、模型路径做成参数。

第 3 步 · 为什么有 ROS 2

白话类比：小饭馆开成连锁店。

一家小饭馆的后厨，规矩是围着"一个厨房、一个领班、几个熟手"定的：谁来上班先去领班那登记，要找谁做菜也先问领班。店小的时候这很好用。可一旦要开连锁、接外卖、半夜也营业、还要过卫生检查，这套规矩就处处不够用。ROS 1 就是那家小饭馆。

ROS 1 是围着一台机器人定的规矩。 ROS 从 2007 年开始，最初是给 Willow Garage 的 PR2 机器人做的开发环境。设计时默认了六个前提（materials/design/articles/010_why_ros2.md §How we got here）：

  1. 只有一台机器人；
  2. 机器人上带着工作站级的电脑；
  3. 不要求实时；
  4. 网络很好（有线或近距离高速无线）；
  5. 用在学术研究；
  6. 完全自由：不规定程序该怎么组织。

ROS 1 里还有一个"领班"：master（roscore 进程）。所有节点先到 master 登记，再通过它找到彼此（同文 §New use cases 称之为 "single-master structure"）。

后来的需求，六个前提全被打破了。 同一篇文章列出了 ROS 1 没想到的用法，每一条 ROS 2 都有对应的答案：

新需求 ROS 1 的难处 ROS 2 的答案 本专题哪里讲
多台机器人一起干活 只有一个 master，多机只能"凑合着改" 没有 master：分布式自动发现（总图 2 第 ② 步）；用 ROS_DOMAIN_ID 分组 阶段 C3
小型嵌入式板子、单片机 只能隔着驱动程序接进来 想让它们也成为正式成员 不展开
实时控制 只能另想办法 设计上支持实时：executor、ros2_control 阶段 C4、F
网络不好（差的 Wi-Fi，甚至天地链路） 没有调节手段 QoS：可靠 / 尽力而为、队列深度、截止时间 阶段 C1
做成产品 实验室原型很难直接变成产品 托管节点（lifecycle）、安全机制、部署工具 阶段 C7、I
需要规定好的写法 什么都不规定 提供明确的模式：生命周期管理、静态配置 阶段 C7、E

还有一个原因：现成的技术成熟了。 2007 年时，ROS 的发现、消息定义、序列化、传输全是自己从零写的。到 2014 年前后，市面上已经有了现成的方案（文中列了 ZeroMQ、Protocol Buffers、DDS 等）。ROS 2 最后选了 DDS（Data Distribution Service，一个工业标准的发布 / 订阅中间件），好处是：

  • 自己要维护的代码少得多；
  • DDS 有成文的标准规范，别人可以审查、可以另做实现。ROS 1 只有 wiki 上的说明和一份参考实现（020_ros_with_dds.md §An End-to-End Middleware）；
  • DDS 自带分布式发现，任意两个程序不需要 master 就能通信（同文 §What is DDS）；
  • 已经有工业产品在用，回答"能不能上生产"时有底气。

代价是：ROS 得在 DDS 的设计框架里干活，不合适的地方要绕过去（同文同节）。这也是为什么要有总图 1 里的 rmw 插座：把 DDS 隔离在下面，以后还能换。现在可选的 Zenoh（rmw_zenoh_cpp）就是一个不基于 DDS 的插头。

为什么不在 ROS 1 上直接改？ 改动太伤筋动骨，会把大家正在用的 ROS 1 弄坏。所以 ROS 2 是另起一套，接口（API）不兼容；需要共存时用桥接（bridge）在两边转发消息（010_why_ros2.md §Why not just enhance ROS 1）。

现状：ROS 1 已停止开发、不再发布新版本，ROS 2 每年 5 月发一个新版本（About-ROS.rst §ROS distributions）。新项目直接学 ROS 2。

关键几行：

sub.queue: deque[bytes] = deque(maxlen=10)   # 订阅队列：满了自动丢最旧的
data = json.dumps(msg).encode()                 # 往下：对象 → 字节（真 ROS 2 用 CDR）
if sub.topic == topic and sub.msg_type == msg_type:
    sub.queue.append(data)                      # 只有名字和类型都对上才放进去
msg = json.loads(sub.queue.popleft())           # spin 时往上：字节 → 对象
sub.callback(msg)                               # 最后才调你的回调

代码里才看得到的 3 件事：

  1. 本机没有 rclpy：ROS 2 在 macOS 上不是 Tier 1 平台，只能源码编译。本书的代码层全部用纯 Python 模拟规则，数字和讲义一致；真 API 留到装好 Linux 环境后做里程碑（R-M0 起）。
  2. 序列化格式：模拟用 JSON，真 ROS 2 默认是 CDR（Common Data Representation：通用 / 数据 / 表示，二进制），第 3 章 bag 里看到的 cdr 就是它。
  3. deque(maxlen=10) 就是 Keep last 10：Python 的双端队列设了长度上限后，再 append 会自动把最左边（最旧）的挤掉。
